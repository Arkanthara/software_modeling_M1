1. Overview: What is verification?

Software verification answers: Does the program meet its specification?

  • Functional properties: what the program computes (correctness of algorithms)
  • Non-functional properties: time, memory, security, usability

We formalize programs with mathematical models and express desired properties in logic so that tools can reason automatically or semi-automatically.

2. Models, Specifications, and the Verification Question

A program source file has syntax (checked by compiler) and semantics (meaning). Compilers generally check syntax; verification tackles semantics.

Notation: Program |= Spec means the program satisfies the specification.

4. A Small Language: Syntax and Semantics

We consider a tiny imperative language with integers and booleans, assignments, if and while, and function calls (simple).

4.1 Operational Semantics (big-step, informal)

  • Memory/state: \(\mu: Var \rightarrow \mathbb{Z} \cup \{tt, ff\}\)
  • \(Val(e,\mu)\): evaluation of expression \(e\) in state \(\mu\)
  • \(Mem(c,\mu)\): executing command \(c\) in state \(\mu\) returns new state \(\mu'\) (if it terminates)

Example:

  • \(Mem(\text{y := 0},\mu) = \mu[y \leftarrow 0]\)

5. Hoare Logic: Triples and Validity

A Hoare triple is written:

\[ \{P\}\ c\ \{Q\} \]

Meaning: if \(P\) holds in the initial state and \(c\) executes (terminates), then \(Q\) holds in the resulting state. Validity: for every state \(\mu\), \(\mu \models P \Rightarrow Mem(c,\mu) \models Q\) (assuming termination).

@startuml
'|title Hoare triple idea
[P: Precondition] --> [c: Command]
[c: Command] --> [Q: Postcondition]
@enduml

Note: Partial correctness excludes termination reasoning. Total correctness includes termination proof (often via variants/metrics).

6. Weakest Preconditions (WP) — definitions and examples

Rules (deterministic language):

  • Assignment: \(WP(x := t, Q) = Q[x \leftarrow t]\)
  • Sequence: \(WP(i_1; i_2, Q) = WP(i_1, WP(i_2, Q))\)
  • Conditional: \(WP(\text{if } b \text{ then } i_1 \text{ else } i_2, Q) = (b \Rightarrow WP(i_1,Q)) \land (\neg b \Rightarrow WP(i_2,Q))\)

6.1 Example: assignment

Program: x := x + 1 and postcondition Q: x >= 1.

Compute WP:

  • \(WP(x := x + 1, x \ge 1) = (x + 1 \ge 1)\)
  • Simplify: \(x \ge 0\)

Thus, the Hoare triple {x >= 0} x := x + 1 {x >= 1} is valid.

6.2 Example: sequential composition

Program:

y := x + 2;
x := y - 1;

Postcondition: Q: x >= 5.

Compute backwards:

  • WP(x := y - 1, x >= 5) = y - 1 >= 5 ⇒ y >= 6
  • WP(y := x + 2, y >= 6) = x + 2 >= 6 ⇒ x >= 4

So {x >= 4} y := x + 2; x := y - 1 {x >= 5}

6.3 Example: Hoare proof with function add(a,b)

Consider the simple loop-based addition (from your notes):

add(a, b) =
  res := a;
  aux := b;
  while aux > 0 do
    res := res + 1;
    aux := aux - 1;
  done;
  res

We want partial correctness: {aux = b & res = a} loop {res = a + b} at loop exit.

Loop invariant candidate: I: res = a + (b - aux) and aux >= 0.

  • Initialization: before loop, res = a and aux = b ⇒ res = a + (b - b) = a. OK.
  • Preservation: assume I and aux > 0 hold, after the body:
    • res' = res + 1 = a + (b - aux) + 1 = a + (b - (aux - 1))
    • aux' = aux - 1
      So invariant holds for next iteration.
  • Termination (when loop ends): aux = 0 ⇒ invariant gives res = a + (b - 0) = a + b. So postcondition holds.

Thus the loop is partially correct wrt the specification.

7. Loops, Invariants and Termination

7.1 Loop invariants (how to choose one)

  • Derive invariant from desired postcondition by working backwards.
  • Invariants must be strong enough to imply postcondition when combined with loop exit condition.
  • For termination proofs, provide a variant (a well-founded integer measure) that strictly decreases each iteration and is bounded below (e.g., aux in the example).

7.2 Example: sum(n) using loop (iterative rewrite)

Recursive sum(n) in your notes can be made iterative:

sum_iter(n):
  i := 0;
  acc := 0;
  while i <= n do
    acc := acc + i;
    i := i + 1;
  done;
  return acc;

Invariant: acc = sum_{k=0}^{i-1} k and 0 <= i <= n+1. At termination i = n+1, so acc = sum_{k=0}^n k = n(n+1)/2.

8. Model Checking — example and counterexample

Model checking verifies properties often expressed in temporal logics (LTL/CTL). A counterexample is a concrete trace showing a property violation.

@startuml
'|title Model checking: counterexample trace
start
:Initial state s0;
if (property holds?) then (yes)
  :Verified;
else (no)
  :Return counterexample trace (s0 -> s1 -> ... -> sk);
endif
stop
@enduml

Small worked example (informal): a mutual exclusion protocol with two processes. Model checker may find a trace where both enter critical section — that trace is a counterexample to mutual exclusion.

9. Abstract Interpretation — example abstract domain

Abstract interpretation uses lattices (e.g., intervals, signs, parity) to safely approximate sets of states.

Interval domain example: Track x as interval [l, u]. For x := x + 1 we map [l, u] -> [l+1, u+1]. This is efficient and safe but loses some precision (e.g., relational facts like x = y + 1).

10. Combining Approaches in Practice

  • Use static analyzers / abstract interpreters for scalable bug-finding (e.g., taint analysis).
  • Use SMT-based verification for verifying small but complex algorithms (e.g., sorting routines).
  • Use model checking for concurrent/finite-state controllers and protocols.
  • Use proof assistants to obtain end-to-end certified proofs when absolute guarantees are required.
@startuml

[Front-end: parse/model] --> [Model checker (finite-state)]
@enduml

11. Additional Examples (detailed)

11.1 Prove min(a,b) correctness

Program:

min(a, b) =
  if a < b then
    res := a
  else
    res := b
  endif;
  res

Spec: returns min(a,b) i.e. res <= a & res <= b & (res = a or res = b).

Use WP for each branch:

  • If a < b branch: post Q becomes Q[res := a] which is a <= a & a <= b & (a = a or a = b) — simplifies to a <= b needed. But since the branch is taken under a < b (stronger than a <= b), the triple holds.
  • If not (a < b) branch: symmetrical reasoning.

Combine using conditional rule and the guard conditions; the triple is valid.

11.2 Example: small program with a failing spec (counterexample)

Program:

x := 0;
y := 1;
if y = 0 then
  x := x + 1
else
  skip
endif;

Spec: final x = 1.

Compute WP: WP(if y=0 then x:=x+1 else skip, x=1) = (y=0 => WP(x:=x+1, x=1)) & (y<>0 => WP(skip, x=1))
- WP(x:=x+1, x=1) = x+1 = 1 ⇒ x = 0.
- WP(skip, x=1) = x = 1.
So WP overall: (y=0 => x = 0) & (y<>0 => x = 1). Before the if, we had x := 0; y := 1 ⇒ state is x=0, y=1. Evaluate WP: since y<>0 branch holds, we need x=1 but x=0. Hence the triple is invalid and a counterexample state exists (the actual run gives x=0 at the end).

12. Practical Tips and Tooling

  • Express assertions and invariants early and keep them simple.
  • Use automated invariant inference when available, but validate them manually.
  • Combine quick scalable analyses (abstract interpretation) with precise checks (SMT) in a staged pipeline.
  • For concurrent systems, model-check small instances to find concurrency bugs (then generalize proofs).

13. Summary

  • Verification is the formal study of program correctness; several approaches exist (deduction, abstract interpretation, model checking, proof assistants).
  • Hoare Logic and WP let us derive preconditions and structure proofs.
  • Loop invariants and variants are central for reasoning about loops and termination.
  • Abstract interpretation trades precision for scalability; model checking trades scalability for exhaustiveness on finite-state models.
  • A pragmatic verification workflow mixes tools to get early feedback (fast over-approx), deep proofs for critical components, and model checking for protocols.
